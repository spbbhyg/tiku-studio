## 1. 画布：#1 滚不到底 / #2 拖到边界抖动

**文件**：`apps/web/src/components/CanvasPane.vue`、`apps/web/src/views/ComposeCanvas.vue`

**根因（两条是同一个病根）**：

```css
.canvas-wrap { display: flex; justify-content: center; overflow: auto; }
```

滚动容器用 flex 居中。内容比容器大时，溢出部分被推向负方向，滚动条只按「居中后」的范围计算 —— 于是出现「没滚到底就停住」。更麻烦的是：

`.canvas-wrap` 一旦出现/消失滚动条，`clientWidth` 就变化；`ResizeObserver` 观察的正是这个元素，于是 `fitScale()` 重算 → 页面尺寸变 → 滚动条再变 → 再重算，**这就是抖动的直接来源**（拖拽改变内容高度时会持续触发）。

**改法**：

1. 滚动容器改 `display: block`，页面用 `margin: 0 auto` 居中，溢出方向正确
2. 加 `scrollbar-gutter: stable`：滚动条常驻占位，`clientWidth` 恒定，从根上断掉振荡回路
3. 底部加 `padding-bottom: 45vh`（约一屏留白，符合验收要求）
4. `fitScale()` 加 0.004 的阈值判断，亚像素差异不再重设；缩放时保持视觉中心，滚动范围由内容高度自然重算
5. 拖拽/缩放期间用 `dragging` 标志冻结自动适配，松手（`nextTick` 后）再校准一次
6. 拖拽上界从 `maxPages * PH` 改为实际 `pageHeight` —— 以前元素能被拖进看不见的空白页，视觉上像「卡住不动」

## 2. 出题界面 #3c：工具栏按钮被面板挤掉

**文件**：`apps/web/src/views/Authoring.vue`（`.wtools` / `.wt`）

**根因**：`.wtools { flex-wrap: wrap }`，窗口一窄就换行，换行后的按钮落到左右面板下方被遮住。

**改法**：`flex-wrap: nowrap` + `overflow-x: auto` + `overflow-y: hidden`，按钮 `flex: 0 0 auto` 不被压缩，滚动条做细并与主题一致（`scrollbar-width: thin` + `::-webkit-scrollbar` 6px）。窗口再窄也只是横向滑动，按钮永远点得到。

## 3. 导出 #4：点导出冒红字

**文件**：`apps/web/src/components/PaperExport.vue`

**根因**：失败分支把 `resp.text()` 原样塞进红框。FastAPI 返回的是 `{"detail":"KeyError: ..."}` 或整段 Python 堆栈，用户看到就是一串红色英文。

**改法**：

- 先按 JSON 解析取 `detail`，取不到再看原文
- 有中文就用中文；纯英文（堆栈）按 HTTP 状态码换成中文说法（`ERR_TEXT` 表）
- `E_XXX` 错误码保留，括在中文后面
- 原始文本只进 `console` 和 `data/logs/app.log`，不上界面
- 红框提供「复制技术细节 / 重试」

配套：`_internal/app/main.py` 增加日志落盘 `data/logs/app.log`（2 MB × 3 轮转）。以后用户说「导不出」，要这个文件就能定位。

## 4. 导出 #5b / #9：Word 里图片放大 + 竖排堆叠

**文件**：`_internal/app/routers/compose.py`（`_docx` → `add_img` 重写为 `add_images`）

**根因（三处，都在 Word 端）**：

```python
w = maxw                                   # ① 没给宽度就吃满版心 → 小图被放大
if width_pt: w = min(maxw, Pt(width_pt))
p = d.add_paragraph()                      # ② 每张图单独一段 → 必然竖着堆
p.add_run().add_picture(..., width=w)      # ③ 没设居中 → 左对齐
```

而预览里同一题的图是一行排开的，所以「预览横排、Word 竖排」。

**改法**：

- 同一题的所有图放进**同一段落的连续 run** → Word 天然横排
- 宽度规则：给了 pt 就用 pt，没给就按图片像素 `px * 72 / 96` 换算，且 `min(版心宽, 原始尺寸)` —— **只缩不放**
- 一行放不下（累计宽 + 12pt 间隔超出 415.6pt 版心）自动换行，行为与预览一致
- 段落 `alignment = CENTER` 居中，`first_line_indent = 0` 去掉继承的缩进
- 图注合并成一段小字（6.96pt，与 `paper.css` 的 `--note-size` 对齐）

## 6. #7 格式转换：从「随机失败」到「说清原因」

**文件**：`_internal/app/routers/convert.py`

**根因（读代码定位，非猜测）**：

1. WPS/Office 的 COM 是**全局单例**，两个转换请求并发就抢锁 → 表现为「有时候能转、有时候转不动」
2. `pdf_merge` 开头无条件 `import pymupdf`、`pdf_split` 无条件 `from pypdf import` —— 便携包只装一个引擎，缺哪个就直接 500
3. 降级链末端用内置 Chromium，浏览器目录没挂到 `PLAYWRIGHT_BROWSERS_PATH` 时报英文异常
4. 加密 / 损坏 PDF 没有单独分类，全被吞成一句「转换失败」

**改法**：

- 重引擎（Office / soffice）串行化加锁，排队执行，忙时返回 `E_BUSY` + 中文提示
- PyMuPDF / pypdf 双引擎自动回退，缺一个不影响
- Chromium 自动挂 `runtime/ms-playwright`，缺了报 `E_NO_CHROMIUM`
- 错误统一成「中文 + ［E_XXX］」，原始异常只进 `data/logs/app.log`
- 新增 `GET /api/convert/diagnose`：报告每个引擎在不在、临时目录能不能写，并给一句人话结论

实测返回：

```json
{"engines":{"office":true,"soffice":false,"chromium":false,"docx":true,"pymupdf":true,"ocr":true},
 "temp_writable":true,"hint":"可以转：将按 office 的顺序尝试"}
```

## 7. #8 题库导入：答案图片丢失

**文件**：`_internal/app/services/bundle_import.py`

**根因**：导入只处理 `q["images"]`（题干图），答案区的图整段被丢掉。而系统本身是有答案图通道的 —— 出题页 `routers/authoring.py` 把答案图也存进 `Question.images`，用 `caption="答案"` 区分，导出时共用同一套取图逻辑。

**改法**：`bundle_import` 接收 `answer_images`，落盘后并入 `images` 并补 `caption="答案"`；文件编号接着题干图续写（`len(images)`），避免 `0000.png` 把题干图覆盖掉。不新增字段，导出侧零改动。

## 8. #10 自动更新：改走国内镜像 + 多源回退

**文件**：`_internal/app/routers/update.py`（整体重写，315 → 574 行）

**根因**：下载走 `api.github.com/.../releases/assets/{id}` 302 到 `release-assets.githubusercontent.com`，拉 **783 MB** 全量包，Range 续传 + 40 次重试。国内这个节点极不稳定，重试全断就只剩一句「下载不完整」。`check` 还有 10 分钟缓存，导致提示与实际不符。

**改法**：

- 三源配置化：清华 TUNA → ghproxy 加速 → GitHub 直连，顺序可在 `data/update/mirrors.json` 或 `TIKU_UPDATE_MIRRORS` 里改
- **先探测再采用**：每源发 `Range: bytes=0-0`，6 秒超时，拿到 200/206 才用；404 静默切下一个（TUNA 的 `github-release` 只收录少量项目，本仓库大概率没收录，不能因为镜像 404 就整体失败）
- 单源续传 3 次 / 30 秒无进展换源，已下载字节在 `/api/update/progress` 实时可见
- 附 `SHA256SUMS` 就校验，不过自动换源重下
- 错误分类：`E_RATE_LIMIT` / `E_NET` / 磁盘不足（说清要多少 GB）/ `E_ALL_SOURCES`（逐个源列失败原因）
- `download()` 不再吃 `check()` 的 10 分钟缓存
- 新增 `/progress`、`/mirrors`、`/log` 三个接口

实测：`GET /api/update/mirrors` 返回三源配置正常。

**构建过程踩了三个坑，都落进了 `vite.config.js`（后续构建直接受益）**：

1. `memory allocation of 440187160 bytes failed` —— `@superdoc/docx-engine` 是 18 MB 单文件，Rollup 默认并发读取时同时持有多个副本，直接 OOM。
   解法：`rollupOptions.maxParallelFileOps: 2`。
2. esbuild 临时文件在 `%TEMP%` 下 `Access is denied`。
   解法：构建前把 `TMP` / `TEMP` 指到项目内 `apps/web/.tmp`。
3. `EPERM: unlink 'dist\ketcher\app.js'` —— Windows 上旧产物被占用，清空目录失败导致整次构建白跑。
   解法：`emptyOutDir: false`，增量覆盖（`index.html` 只引用新 hash，旧 chunk 留着无影响）。
